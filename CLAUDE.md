# Project PickleVision

Computer-vision pickleball line-calling/analytics system (Cpe-401 thesis project). Team: Merl, Franz, Arjhon. All tracking logic lives in the single file `tracker.py`.

## Setup

Follow `requirements.txt`'s header comment exactly — install order matters (`inference` drags in a CPU-only `onnxruntime` that must be overwritten last with the GPU build). No CUDA Toolkit/cuDNN system install needed; the NVIDIA libraries come from pip. First launch of `--roboflow-local` with TensorRT available builds an optimized engine for that specific GPU (~4-5 min, one time only, then ~17s on later launches) — don't panic if it looks stuck.

Roboflow model: `pickleball-prototype/3` (workspace `franzs-workspace-utuz0`), weights cache into `./model_cache` after first fetch (offline after that) -- or `%LOCALAPPDATA%\picklevision\model_cache` when the project's path isn't plain ASCII (see Known gotchas).

## Hardware / camera architecture

**Finalized 3-camera plan** (from the thesis panel, not written in `Cpe-401_Grp3_Proposal Paper.pdf`): two cameras at opposite baseline ends of the court facing each other (the ELP 120fps USB camera + one more), plus one overhead camera mounted above mid-court looking straight down. The three roles are NOT interchangeable:

- **End cameras (2)** — best source for *when* a bounce happens (Y-axis trajectory-reversal logic in `_detect_ball_contact`, needs an elevated side-on angle). Each covers its own near half only (baseline to net) via `--court-length 22` half-court calibration — higher detail per half than one camera straining across the full 44ft, plus free redundancy (a player blocking one end's view is unlikely to block the other's).
- **Overhead camera (1, not yet acquired)** — best source for accurate ground-plane (x,y) for the actual IN/OUT call (near-orthographic homography, minimal distortion), but Z-blind: cannot tell ball height, so cannot detect bounce timing on its own. Needs a pole/truss/ceiling mount, not a tripod — a real infrastructure ask the end cameras don't have.
- Fusion rule (implemented for the 2 end cameras in `DualCameraFusion`): whichever end camera currently has the ball on its own near half is the timing/position source for that half; the overhead camera, once added, is the line-call authority regardless of which end camera flagged the bounce.

**Coordinate unification across the 2 end cameras** (see `to_global_court_point`/`check_camera_alignment` in `tracker.py`): each end camera calibrates its own half independently (local Y in [0, 22], 0 = net). To get one global court Y in [0, 44] (0 = end-A baseline, 22 = net, 44 = end-B baseline): `global_y_A = 22 - local_y_A`, `global_y_B = 22 + local_y_B`. **X is mirrored for camera B**: `global_x_A = local_x_A`, `global_x_B = 20 - local_x_B`. The two cameras face each other, so B's left is A's right, and each calibration puts local X=0 at the left of its own image (`--calibrate`'s TOP-LEFT is clicked as seen on screen). Mounting both centered on the centerline does NOT make "left" consistent (an earlier version of this file assumed it did, and passed X through unchanged): centering only makes the mirror symmetric about the centerline, so the old math agreed only for points ON the centerline and was off by 2*(10 - x) ft elsewhere -- 10 ft for a point 5 ft from a sideline. Verified with simulated centered cameras (and it's what `--check-alignment` would have reported as MISALIGNED for any spot off the centerline). Centered mounting is still worth doing -- even coverage of both sidelines -- just not for the math.

**Compute:** this dev laptop has an RTX 3050 (4GB VRAM); Franz's laptop has an RTX 4060 (measured 3 concurrent 720p streams at 120+ FPS each, well above what's needed). Benchmarked on the RTX 3050 with the real Roboflow model end-to-end: 1080p = 41.3 FPS, 720p = 85.2 FPS single-stream — 720p is the resolution to target for multi-camera headroom on this machine (and `--width`/`--height` now default to 1280x720). Another laptop has an RTX 4050 (6GB): with GPU torch, rendered 720p footage runs single-camera at 106 fps with the person filter on (the default; it re-runs ~30x/s, its boxes reused in between -- 68 fps when it ran every frame) and 202 with `--no-exclude-people`; dual (`--source2`) from two paced 120fps sources ~80-90 steps/s, ~100 frames/s processed per camera (see Dual build); the Roboflow model alone is ~2.7 ms/frame on TensorRT (~4.8 with its pre/post-processing), the person filter ~5-9 ms.

**Open idea, deliberately held:** run the 2 end cameras at 720p but the overhead camera at 1080p (it covers 2x the court area of one end camera's half, so needs the extra resolution for comparable detail-per-foot — and it's the camera whose accuracy matters most for the actual line call). Current code doesn't support per-camera resolution yet (`--width`/`--height`/`--fps` are single global flags shared by every camera). Before building this: have Franz benchmark a mixed sequential stream (2x720p + 1x1080p) on his RTX 4060 — don't assume from the RTX 3050's uniform-resolution numbers, since part of the 1080p-vs-720p gap may be CPU-side frame capture/resize rather than pure GPU model cost.

**Dual end-camera build** (`--source2`, `DualCameraTracker`): one `PickleVisionTracker` per end camera, on two threads, sharing one loaded Roboflow model. Both balls are mapped to global court coordinates and bounce flags are fused into line calls on the full 20x44 court:
- **Timing is by capture time, not processing step.** Live, each step takes whichever cameras delivered a new frame (`_SyncedFrames`) -- a slower camera (an ELP drops to 60fps or less in dim light) is processed less often instead of holding the other to its pace; from video files, frames go in capture order by the `.timestamps.csv` `--record-raw` saves beside each video (else frame number / fps; frame-N-with-frame-N drifted 167 ms in 10 s between a 120 and a 118fps camera). Each frame carries its driver's capture timestamp (MSMF `CAP_PROP_POS_MSEC`, on the `perf_counter` clock) -- a laptop webcam hands frames over 80-270 ms after capture, varying frame to frame, so arrival order doesn't line two cameras up. `CaptureTimeAligner` feeds the fusion in capture-time order, pairing each camera's ball with the other camera's interpolated to the same instant, and each bounce flag at its landing frame's time (not the few frames later it's raised, when the ball is back in the air). Simulated 7 shots x 10 seeds (2px jitter + 2px clicks), old pairing-by-step vs now: unsynced 120fps 68 -> 69/70; B's driver 60 ms slower 52 -> 70; B's latency varying 0-100 ms 41 -> 70; B at 60fps 67 -> 69; live with ~3 of 4 frames processed 67 -> 68 (same through `DualCameraTracker._update` and the real per-frame code: 68-70/70).
- **Throughput and timing:** the GPU is the limit (shared model, ~2.7 ms/frame; the second copy of the model gained nothing). Two paced 120fps sources on an RTX 4050 Laptop: ~100 frames/s processed per camera (before: 50-65 pairs/s). The person filter runs on a worker thread for live sources (`async_person_filter`; video files stay synchronous and reproducible), and the combined view is only composed at `DISPLAY_FPS` (30) unless recording. Since not every frame gets processed, `track_processing_rate` re-times the bounce detector's frame-count settings to the rate actually processed (single camera too): in simulation at 60 processed fps, 89/120 landings right timed for 120 vs 98 timed for 60; at 40, 70 vs 93.
- The ground check: a ball on the ground maps to the same court point through both homographies, a ball in the air to two points pushed apart (away from each camera) -- ~7 ft apart per foot of height with cameras 15 ft back and 10 ft up. So the gap between the two cameras' positions bottoming out near zero IS a bounce, and a camera's own `_detect_ball_contact` flag that the other camera sees happening in the air is a hit or the top of an arc, not a bounce (ignored, counted in the summary). In simulation the old frame-to-frame `_detect_ball_contact` alone caught only 4/7 of the test bounces (a far-off ball traveling along the court moved under its 3px-per-frame jitter threshold at 120fps); the rewritten one (see Single camera) catches 7/7 on its own, and with the ground check 88-89/90 runs are right with 2px detection jitter + 2px calibration click error, with no false calls from a resting or rolling ball.
- The ground check's landing spot weights the two readings by the cameras' distances (`_ground_point`, `CAMERA_SETBACK_FT` 15): its low-point sample is up to a frame before contact, the ball slightly up, and each camera pushes a raised ball away from itself -- the home camera's reading alone was 1.1-1.4 ft off for a dink with one camera at 60fps.
- Calls are `CONFIRMED` (both cameras put the ball there as it bounced) or `SINGLE` (only one camera saw it -- only as reliable as that camera's own detector). `--bounce-agreement-ft` (default 3) is the tolerance.
- Shown as both feeds side by side over a top-down court diagram; `--output` records that view, `--raw-output`/`--raw-output2` each camera's raw footage in sync.
- Verified end to end with the real Roboflow model on rendered two-camera footage of a rally (serve IN, return IN, long ball OUT): all three called correctly, 0.07-0.32 ft from the true spots. Not yet on real cameras/court.

**Single camera** (bounce detection rewritten; tuned and checked in a physics simulation of a 12-landing session -- six within 0.5 ft of a line -- seen by one 120fps camera with 1.5px detection jitter, 8% missed detections and calibration click error, fed through the tracker's real per-frame code):
- `_detect_ball_contact` finds the ball's low point in the image (a V) -- or a kink, the sudden slowdown of a ball coming toward the camera that keeps moving down the image through its bounce -- using lines fitted over 8 real detections each side at 120fps (scaled with frame rate by `set_frame_rate`), whose slopes must clear the jitter they leave by 2.5 standard errors. It rejects a fast turn-back in X (a paddle, not the ground), windows with a position jump (lock hopping), and landings mapping >10 ft outside the calibrated court; reports each bounce once; and puts the landing where the fitted lines cross, at the ball's BOTTOM (box half-height below its center -- mapping the center put landings 3-6 in too far from the camera, the largest single error). The old detector (any frame-to-frame direction change, plus a "speed dropped under 4px/frame" rule) got 22/60 landings right with 694 false calls over 5 simulated sessions from behind a baseline: every top of an arc, and a ball held still before a serve, counted.
- Placement matters: from the side of the court a bounce is always a down-then-up in the image. `--view side` (calibrate and track with it; TOP edge clicked = the far sideline): 95% of landings right, 99% with careful calibration clicks (98% of those within 0.5 ft of a line), ~1 false call per 20 sessions. From behind a baseline: 85% / 88%, no false calls -- it misses flat drives racing away (no V, no kink toward "down").
- Calibration precision is most of the remaining error, hence the calibration tool's 8x magnifier and arrow-key nudging; click the OUTSIDE corner of the painted lines (lines are in).
- Not yet verified on a real court. Rendered-video tests can't judge detection: the model finds a drawn ball well far away but almost never up close (unlike a real ball), so those renders only test plumbing.

## The CLI commands

0. **Find the cameras**: `python tracker.py --list-cameras` -- each index that opens and the frame rate it really delivers (the ELP is the one doing ~120)
1. **Live tracking**: `python tracker.py --source 0 --roboflow-local --court-corners "..." --court-length 22`; from beside the court: `python tracker.py --source 0 --roboflow-local --view side --court-corners "..."`
2. **Calibrate homography** (interactive, click 4 court corners): `python tracker.py --source 0 --calibrate --court-length 22 --calibration-output corners_a.txt` (`--view side` for a camera beside the court: full court, TOP edge = the far sideline)
3. **Dual end-camera alignment** (`--check-alignment`): without calibrations, live center/level guides for physically aiming both cameras straight down the centerline; with them, each calibrated court drawn over its feed (the far half extrapolated too), an aiming readout ("Next: pan left" / "rotate clockwise ~1.2 deg" / "move right ~0.8 ft"), and click-the-same-spot-in-both-feeds verification: `python tracker.py --check-alignment --source 0 --court-corners "$(cat corners_a.txt)" --source2 1 --court-corners2 "$(cat corners_b.txt)"` (`--court-length` defaults to 22 whenever `--source2` is given)
4. **Dual end-camera tracking**: `python tracker.py --roboflow-local --source 0 --court-corners "$(cat corners_a.txt)" --source2 1 --court-corners2 "$(cat corners_b.txt)" --width 1280 --height 720`
5. **Lens calibration** (`--calibrate-lens`, once per physical camera, per resolution): click 4-8 points along each of 3+ lines that are straight in reality (sidelines, baseline, kitchen line, centerline, fence rails), 'n' between lines; the fitted correction is drawn back over the feed so it can be checked against the paint ('v' = straightened preview). Saves `lens_cam<source>.json`: `python tracker.py --source 0 --calibrate-lens`. Then pass `--lens lens_cam0.json` to `--calibrate`, tracking and `--check-alignment` (`--lens2` for `--source2`'s camera).

**Lens correction** (`LensModel`, `fit_lens_from_lines`): the ELP-style USB cameras are wide-angle with visible barrel ("fisheye") bend -- court lines bow outward, and a 4-corner homography (straight lines only) is exact at the clicked corners and off in between. `CourtMapper(lens=...)` straightens every image point (clicked corners and ball positions) before the homography and bends court lines back for drawing, so callers keep using raw pixels and existing `--court-corners` strings stay valid (just recalibrate the corners with `--lens` for best results). Fitted from the court's own lines (plumb-line method: OpenCV radial k1/k2 about the image center, nominal focal) -- no checkerboard needed, which suits these fixed-focus cameras (a phone/board close to the lens would be out of focus). In simulation of an end camera 15 ft back, 10 ft up: court-position error mean/max 5.3 / 13.4 in -> 1.4 / 5.3 in for a strong fisheye, 2.7 / 7.6 -> 0.8 / 2.0 in for a medium one, unchanged with no distortion. On the real camera's court footage the corrected baseline follows the bowed paint where the straight line sat above it mid-court. A lens file only fits the resolution it was made at (`_load_lens` refuses a mismatch). Combines with `--view side` (`CourtMapper(lens=..., view="side")`): in simulation a strong fisheye seen from the side put court positions 3.8 in off on average (7.2 max) uncorrected, ~0 corrected, and the single-camera line-call accuracy with correction matched a distortion-free lens.

6. **Record raw footage** (`--record-raw`): camera frames only -- no detection, no overlays, MJPEG `.avi` written on a background thread, each frame's driver capture time in `FILE.timestamps.csv` beside it -- so it keeps the camera's full 120fps where recording inside the tracker (or a screen recording) lags. Replay through the tracker as many times as needed with `--source FILE.avi`: `python tracker.py --source 0 --record-raw recordings/raw1.avi` (`--record-seconds N` to stop by itself). With `--source2`, both cameras at once into `raw1_A.avi` / `raw1_B.avi`, replayed in sync by their capture times: `python tracker.py --roboflow-local --source recordings/raw1_A.avi --court-corners "$(cat corners_a.txt)" --source2 recordings/raw1_B.avi --court-corners2 "$(cat corners_b.txt)"`. The capture times also time detection to the rate the camera really delivered. Use this, not screen recordings, for anything that tunes detection: a 30fps screen capture with the old overlays baked in can't be re-run.

Single camera with a half-court calibration (`--court-length 22`, end view) doesn't call bounces mapping past the net (`half_court_only`; dual mode turns it off). In screen recordings of the old detector (ELP behind a baseline, near half calibrated), most wrong OUT calls on a ball in the air were exactly that -- mapped -8 to -134 ft beyond the net -- the rest were arc tops/hits (fixed by the rewritten detector) and balls from the neighbouring court (not yet handled). For one camera calling both halves, calibrate the full court (`--court-length 44`) or use `--view side`.

## Known gotchas

- `OPENCV_VIDEOIO_MSMF_ENABLE_HW_TRANSFORMS=0` must be set (it is, at the top of `tracker.py`) or `cv2.VideoCapture` on Windows takes 50-60s to open a USB camera.
- A phone running Camo (camo.com) works fine as a temporary second webcam for testing — it shows up as a normal `cv2.VideoCapture` index, no code changes needed. Just watch for USB-vs-WiFi latency and free-tier resolution/fps caps vs. the real ELP camera's 120fps MJPEG capability.
- Never attempt to bypass Roboflow's weights-export paywall — `--roboflow-local`/`get_model()` is the legitimate offline path already in use.
- Install the GPU build of torch (last step in `requirements.txt`). torch runs the person filter -- on by default -- and with the CPU build it was the bottleneck: ~60 ms/frame per camera, CPU pinned at 100%, 26 fps single-camera / 14 dual on an RTX 4050 laptop (68 / 38 on the GPU). torch 2.14 only has a CUDA 13 build, and it brings its own cuDNN with the same DLL names as onnxruntime's pinned cuDNN 9.7: `import torch` must stay before onnxruntime's DLL preload (the other way round, torch fails to import), and the preload then skips cuDNN -- onnxruntime runs on torch's, checked correct on both TensorRT and plain CUDA.
- onnxruntime's TensorRT provider can't create its engine cache under a non-ASCII path (e.g. a Japanese-locale Windows' OneDrive Documents folder): it logs "EP Error create_directory: The system cannot find the path specified" and silently falls back to plain CUDA (~2x slower). `tracker.py` now defaults `MODEL_CACHE_DIR` to `%LOCALAPPDATA%\picklevision\model_cache` whenever its own folder's path isn't ASCII.
